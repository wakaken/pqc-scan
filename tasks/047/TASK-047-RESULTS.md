# TASK-047 入力を壊して調べるファジング試験

047では、公開・合成データの一部を書き換えたり、途中で切ったり、繰り返したりして、pqc-scanが異常終了・停止・不整合を起こさないか調べます。正しい入力を決めて渡す通常のテストに、予想していなかった壊れ方を探す試験を加えます。

## 対象と確認内容

| 入力群 | 通す処理と主な確認 |
| --- | --- |
| DER・SPKI | 公開証明書と公開鍵の属性解析、検出器。不明OIDから鍵長を推測しない |
| PEM | 公開証明書と合成の秘密鍵マーカー、通常の検出器。秘密鍵本体は用意しない |
| PKCS#12 | 公開証明書だけの合成コンテナー、破損・暗号化・混在例の状態 |
| SBOM・依存情報 | CycloneDX・SPDX、manifestとlockfileの既存対応形式・版 |
| 設定 | nginx・Apache・Envoy・Ingress・Istio・HAProxy・Traefik |
| ソース | Java・Go・JavaScript・TypeScript・TSX・Python・Rust・Ruby |
| 出力 | JSON読込、native inventoryの参照検証と往復、CycloneDX 1.7のSchema、従来6出力の英日生成と合成秘密の伏せ字 |
| protocol | SSHの識別行・packet・KEXINITと往復、TLSのrecordを通常の証明書検証設定で読み込む処理 |

055の74入力を再利用し、公開証明書から取り出したSPKI、不明OID、出力の正例・破損例、合成のTLS/SSHバイト列を加えます。TLSとSSHを分け、8入力群を9対象として実行します。加えて、資産・観測・参照関係が入った既存の出力例についても、時刻・実行IDを整えた正例、壊れた参照、未知の語彙の3入力で短長の追加測定を行います。TLSは新しいclientに未要求のrecord列を渡す試験で、相互の通信やTLS状態機械の全経路を探索するものではありません。SSHでも鍵交換の実行はしません。

パーサーが壊れた入力を拒否すること自体は失敗ではありません。拒否・部分処理・対象外・未知をそのまま記録します。異常終了、時間切れ、所見の別ファイルへの誤帰属、壊れた出力・参照、認識済みの合成秘密の流出などは、確認が必要な失敗として残します。

## 実行の上限と再現

057の隔離基盤と入力ごとの監督処理を使います。入力は最大1MiB、1回は実時間2秒・CPU時間2秒です。子孫を含むメモリ・PID・作業領域は外側のコンテナーで制限します。通常の暗号検証を弱めず、新しい工具・依存は導入しません。

短時間は30秒または256入力、長時間は120秒または2,048入力の、先に到達した上限で止めます。計画にあった30分/対象は費用確認前の案でした。初回は9対象を短長の両方で実行し、合計の最大時間を約23分、入力数を20,736件に抑えます。資産・観測入りの出力の追加2枠を含めると、最大約25分・23,040入力です。これは初回の探索枠で、品質の合格閾値ではありません。制限に達したら終了し、定期実行やCIへの追加は行いません。

seed・PRNGのseed値・入力番号・ファイル名・入力hashを保存します。同じ保存seedと番号から変異入力を再生成できます。成功時の一時ファイルは削除し、処理状態と終了結果をJSONLにまとめます。失敗時は元入力・ログを残し、別プロセスで同じ失敗を再現してから、小さくした入力でも再現するか確かめます。

縮小はバイト列の削除を繰り返す方法です。1バイトの削除でも同じ失敗が消えるところまで調べますが、任意の書き換えを含めた世界最小の入力は保証しません。縮小も30秒・256回で制限し、終わらなければ最小性は未確認とし、完了扱いにしません。意図的に`CRASH`を含む入力で失敗する対照プログラムを使い、保存・再現・縮小の経路そのものも検証します。この対照の失敗は製品の不具合に数えません。

## 結果の読み方

今回の変異は固定seedに対する決定的なバイト変異です。実行時の分岐情報を使って次の入力を選ぶcoverage-guided fuzzingではありません。処理状態の件数と、後述するソースの到達率は分けて記録します。短長で同じseedを再実行するため、実行件数を独立した入力数や精度の標本数とは扱いません。

20枠・14,547入力を実行し、異常終了・時間切れ・試験で定めた検証条件の違反は見つかりませんでした。対象・入力名・バイト列を組にした重複なしの入力は12,133件、バイト列だけでは11,667種類です。全ての記録を再生成してhashを照合し、短長の各枠で保存した全seedが実行されたことを確認しました。

## 255入力による到達率の追加計測

044の計測方法と集約処理を再利用し、各対象の全seedと続く16変異、計255入力をRust 1.93.1の`-C instrument-coverage`で再実行しました。通常ビルドと同じ入力hash・処理結果になったことを全件で確認しています。過去の044の成績を今回の成績には使っていません。

リンクされたRustソース75ファイルの範囲で、行は6,080/18,975（32.0%）、regionは9,371/30,312（30.9%）に到達しました。分母にはソース内のテスト用コードも含まれます。リンクされなかった11ソース、依存ライブラリやFFIのCコードはこの分母に入りません。branchは未計測で、regionをbranchに読み替えません。この値は255入力の追加計測の結果です。

追加計測は、LLVMのカウンターファイルと通常実行の終了処理に干渉しないよう、専用の隔離実行へ分けました。計測時だけファイル上限を16MiBにし、通常の探索は2MiBのままです。CPU・実時間・子孫を含む外側の上限と、通常の暗号検証は維持しています。ビルド時のカウンターは対象実行の集計から除外しました。初回の上限超過と、並行計測中のソース回収による失敗はログに残し、測定側の失敗として区別しています。専用実行は終了0、ソース前後一致、後始末まで成功しました。
