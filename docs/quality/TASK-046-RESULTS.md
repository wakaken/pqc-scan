# TASK-046 生成入力による統計・ID・不明状態の検証

046では、入力の組み合わせを増やして、pqc-scanの検査統計・ID・不明情報の扱いが崩れないか確かめました。前提となる055の評価と二段階レビューを完了してから着手しました。

## 生成する入力と確認内容

新しい依存やテスト基盤は導入せず、055のテスト用fixtureと元のpipelineを再利用します。固定した3つのseed（46、20261113、1592642302）から、次の入力を生成します。seedと入力は結果に保存します。

| 入力 | 確認すること |
| --- | --- |
| 空集合、8種類の処理状態、最大8ファイルの混合192例 | 選択・読み取り・各終端の件数が入力事実と一致し、失敗や不明を完了扱いにしない |
| 同じ入力を別の一時ルートと並列度1・2で再実行 | 所見、統計、診断、資産、観測、参照関係が意味的に再現する |
| native出力の読み直し | JSON往復で事実を保持し、未知の語彙を勝手に既知の値へ変えない。壊れた参照は拒否する |
| 空文字・区切り文字・Unicode・NULを含む384例のID入力 | 同じ入力のIDが安定し、異なる要素列や要素数・domainが区別される |
| 未知の名前、既知名に似せた未知の名前 | アルゴリズム名や量子耐性・用途を推測で補わない。既知のRSAを受け入れる正の対照も確認する |

IDについては384例に加え、長さ0・1・127・128・129の境界も確かめます。各入力から複数のIDを作り、別の要素列が同じIDへ潰れないことを確認します。有限の衝突検査であり、SHA-256の衝突耐性の証明ではありません。

## 再現性で比較する範囲

所見ID・資産ID・対応キーは変えずに比較します。生成時刻と実行情報を比較から外し、仕様上スキャンごとに変わる観測IDだけは、その参照も一緒に対応付けて比較します。元の出力を先に検証し、壊れた参照を正規化で隠さないようにしています。それ以外の事実は保持します。

初回は観測IDも実行をまたいで同一であると仮定したため、1ファイルの入力で比較に失敗しました。差分を調べると観測IDとその参照だけが異なり、[Inventory v1の契約](../architecture/INVENTORY-REPORT-V1.md)で実行単位のIDと定めていることを確認しました。製品コードは変えず、比較方法を契約に合わせています。この開発中の失敗を、製品の不具合には数えません。

## 失敗例の縮小

入力リストから要素を1つずつ取り除き、失敗が残る場合だけ小さい入力を採用します。これを繰り返し、1要素も取り除けない反例まで縮小します。全ての種類の最小入力を保証する手法ではなく、今回のファイル状態リストを縮める処理です。

動作確認には、意図的に誤った「所見0件なら検査完了」という仮説を使います。元のpipelineで実行すると、所見0件でも検査状態が不明な場合があるため、この仮説は失敗します。対象外・不明・対象外の3ファイルから、不明な1ファイルまで縮小できることを確認します。空集合にすると失敗しなくなることも確かめます。誤った仮説は負の対照だけに使い、製品に入れません。

通常の生成試験で検証条件の違反を見つけた場合も、seed・元入力・縮小入力・理由を保存して試験を失敗させます。環境や予期しないpanicなどで試験が中断した場合を、合格にはしません。
