# develop取り込みの検証記録

対象は、v0.3の品質評価ブランチへのv0.2リリース済みdevelopの統合です。両親コミットと完了条件は[作業計画](PLAN.md)に記録しています。本書は今回の確認結果を追加するもので、042・043の過去の測定や正解ラベルを置き換えません。

## 競合と修正の理由

6ファイルで競合しました。検出器の登録、正規表現検出器、構文解析検出器、ルール品質metadata、自己スキャンの有限許可一覧、ルール説明文書です。片方を選ぶのではなく、それぞれの変更を統合しました。

統合時に再現した不整合は次のとおりです。

- **検査予算**: 043の局所解析には32所見、4,096候補、8,192-byte証拠などの固定上限があり、v0.2の公開予算と一致しませんでした。ノード、候補、照合数、所見数、照合対象バイトを既存の`DetectorBudget`から受け取るようにしました。小さい予算での中断、既定値での完走、拡大した予算での継続を確認しました。
- **構文対応**: 構文解析検出器が受け入れるTypeScript・TSX・module構文を、正規表現検出器の局所解析だけが構文エラーとする状態でした。テンプレートの検査限界も含め、同じ解析準備処理を使うようにしました。元ソースの位置と証拠は維持します。
- **Ruby依存関係**: 両ブランチで別々のgemspec解析が追加されていました。v0.2の専用Ruby解析に統一しました。依存名だけが固定の場合は、その名前を残し、動的バージョンを不明、検査状態をPartialとします。値の実行・推測は行いません。
- **証拠の版**: ルールは122件に増えています。現在のYAMLに品質metadataを束縛し直しました。v0.2自己スキャンの過去の測定は保存し、古いsource hashと一致しないファイルの所見を自動除外しないことを確認しました。過去のSARIF例を用いる単体テストには、既存の合成ソースfixtureを使います。
- **042の適用範囲**: 公開COVERAGE文書が更新されたため、旧レビューのhashを現在の文書に付け替えることはできません。現在の契約と入力から、別の2名で再確認し、別ディレクトリに保存しました。元のnominal採点は保持します。

現在の既定上限は、規則・ファイルあたり4,096所見、65,536照合候補、ファイルあたり262,144 AST候補・2,000,000ノード・256 MiBの照合対象です。alias深さ8、有限配列32要素、解析深さ64など、局所的な推論の制限は残します。旧043仕様の固定32所見等は取り込み前の条件であり、現在の公開予算を示すものではありません。

042の6属性単位は、旧P12/PFXの暗号化contentを対象とします。元DERから名目的に分かる属性と、現在の非復号スキャナーが対応する入力範囲は別です。二者が全246単位の元入力・契約を再確認し、6単位のみ対応範囲外、残り240単位は元の範囲を維持すると判断しました。[新しい適用範囲記録](../../../tests/quality/applicability-042-develop-integration/assessment.json)をCIの参照先にし、旧レビューとnominal採点を保存しています。supported-scopeの98 / 2 / 0 / 91は、この適用範囲の違いを示す値で、検出器改善の値ではありません。

全検出結果の件数は一部変わっています。v0.2由来のEC・EdDSA API規則が追加され、TLS境界と証明書コンテナの扱いが修正されたためです。これらは各コーパスで指定した採点対象との違いを含みます。追加・削除された規則、位置、証拠をCOMPARISON.jsonに保存しました。

## 性能と出力量

同じRust 1.93.1のreleaseビルド、同じMac上の既存ハーネスで、初回1回と追加3回を測定しました。キャッシュの完全制御、実行順の無作為化、他ホストでの測定はしていません。[性能記録](PERFORMANCE.json)は記述的な比較であり、一般的な性能保証ではありません。

通常のsmall/medium/largeでは、取り込み前に対するwall time中央値は1.19 / 1.43 / 1.27倍でした。別途、取り込み元のdevelopをgit archiveから独立にoffline buildし、同じ入力でも測定しました。統合版/develop単体は約1.00 / 1.10 / 1.00倍です。統合版には043の追加検出・解析もあるため、同一の仕事量と仮定した性能同等性は主張しません。

大量一致のpathological入力では、取り込み前の128所見・約1 MB出力から、統合後は16,384所見・約122 MB出力になりました。既定の所見上限が32から4,096へ増えた影響が現れています。wall time中央値は約0.027秒から0.850秒、peak RSS中央値は約16 MiBから315 MiBへ増えています。既存の2倍シグナルを超える**Investigation Warning**として残し、従来と同じコストとは扱いません。

同じ入力でdevelop単体も16,384所見、約0.850秒、約315 MiBでした。統合版/develop単体のwall time比は1.00008、RSS比は1.00104です。この負荷の大幅増加は今回の統合で新たに起きたものではなく、v0.2の公開予算と出力量に伴うものと切り分けました。既存の予算や品質ゲートは変更していません。

## 自己スキャンと確認の限界

自己スキャンとCode Scanning用の整形は終了0でした。1,831所見のうち、既存の有限レビューに一致する1,422件をupload用コピーから除き、409件を残しました。生SARIFは保存しています。3ファイルでは過去の除外記録のsource hashが現在と一致しないため、その所見を除外していません。合成入力・新しい規則・移動したテストも含む残存409件の全件安全性審査は、今回実施していません。結果ゼロや製品の安全性を主張するものではありません。

ホスト上でGitHub Actionsそのもの、任意機能の完全な隔離プロトコル行列、新しいブラウザlayout観測は実施していません。品質レポートのQ1〜Q6やreleaseDecisionに残るPartial / Unknown / Not Testedは、製品全体への保証範囲を表します。今回の統合の未完了を意味する値ではありません。今回の統合条件は、計画で定めた検証と二段階レビューに対して判定しています。

## 証拠と対象ソース

- 取り込み前の退避バイナリとruntime source bindingsは、[直前の検証済み記録](../task043-maintainability-20261112/SOURCE-MATCH.json)と完全一致しました。
- 最終測定はマージ確定前の作業ツリーで実行したため、environmentのHEADは取り込み前コミット、worktreeは統合差分を示します。最終実装の識別にはruntime source digestと各ファイル・バイナリのhashを使います。マージ後もこの対応を確認します。
- git archiveで取り出した取り込み前・develop単体のソースの測定では、Gitコマンドは親checkoutを観測します。ソース自体はarchive由来のファイルhashで識別し、Gitのworktree表示を旧ソースのclean確認には使いません。開始時のclean状態はENTRY.jsonに記録しています。
- 生データとログは `target/develop-integration-20261112/` に保存しました。精度採点の生JSON・環境・性能の測定JSON・実行ログはRAW-EVIDENCE.tar.gzにも保存し、[証拠索引](EVIDENCE-INDEX.json)にhashを記録します。大規模な性能試験のレポート本文はGitに重複保存せず、ローカルのtargetとEXTENDED-EVIDENCE.tar.gzに残しています。再測定時は既存ディレクトリを上書きせず、新しいout-dirを指定してください。
- [実装レビュー](IMPLEMENTATION-REVIEW.md)、[テスト妥当性レビュー](TEST-REVIEW.md)、[測定環境・source bindings](AFTER-ENVIRONMENT.json)から、今回確認した範囲を追跡できます。

Cargoの製品版はdevelopから取り込んだ`0.2.0`のままです。このブランチの品質評価ロードマップがv0.3向けであることと、次の正式リリースを実施したことは別です。公開・push・タグ付けは行っていません。
