# TASK-045 変異試験

045では、pqc-scanの重要な処理に意図的な誤りを入れ、既存テストがそれを検出できるか調べました。044が「処理が動いたか」を調べたのに対し、045では「動いた処理の誤りを見抜けるか」を確かめます。

対象は、重大度の調整、ルール一致、読み取り失敗、検出結果の正規化、証明書属性、検査の完了判定、秘匿の7領域です。既存ロードマップの初回案に沿って20件を選びました。無作為抽出や全コードの変異の列挙ではないため、製品全体のテスト品質を表す値にはしません。

## 方法と判定

変異の一覧は[固定した入力](../../tests/quality/task045/mutations.json)にあります。変更前の文字列が対象ファイルの1箇所だけにあることを確認し、ソースのコピーに1件ずつ変更します。製品の元ソースやルール、公開形式は変更しません。

新しい変異生成ツールは導入せず、既存の共通コンテナー基盤を使います。対象環境はLinux arm64、Rust 1.93.1、全機能有効です。外部通信なし、非root、元ソースとルートファイルシステムは読み取り専用で、メモリ6 GiB・追加swapなし・CPU 2・PID 128・作業領域4 GiB・成果物64 MiB以内の条件を維持します。変更するのはコンテナー内の作業用コピーです。

無変異の対照テストが成功してから測定します。まず該当crateの単体・結合テストを使い、見逃した変異はworkspace全体のテストバイナリでも確認します。doctestは含みません。ビルドとテスト実行は分け、テストを1件も実行していない結果は見逃しと数えません。1件ごとに元のソースへ戻し、最後に復元後の対照を実行します。

| 判定 | 意味 |
| --- | --- |
| caught | 変異を入れると、実行されたテストが失敗した（アサーション失敗や予期しないpanic） |
| missed | 変異を入れても、対象テストが全て成功した |
| timeout | ビルドまたはテストが時間上限に達した。検出成功とは数えない |
| unviable | 変異を入れたコードがビルドできなかった。検出成功とは数えない |

実行環境や計測処理の障害は上の4分類に押し込まず、評価を止めて原因を確認します。検出率の基本の分母はcaughtとmissedの合計です。時間切れとビルド不能は除外し、件数を別に表示します。意味が変わらない変異があれば、根拠を示して区別します。

Miriは使いません。計測結果は今回のソース、入力、設定、選んだ変異に対するものです。テストの成功や高い検出率だけで、暗号判断の正しさや製品全体の安全性を保証するものではありません。

## 見逃した変異の意味

| 変異 | 変更の影響 | 追加すると有効なテスト |
| --- | --- | --- |
| M03・M04 | Info→Low、Low→Mediumの昇格を省いても成功した。既存のMedium→Highや秘密鍵→Criticalのテストだけでは、この2経路を確認できない | 高信頼・対象カテゴリ・量子脆弱の条件で、秘密鍵以外の検出を使い、Info→LowとLow→Mediumをそれぞれ確認する |
| M09 | 検出結果に入れる確信度を0にしても成功した | ルールに指定した確信度が、正規化後の所見にもそのまま残ることを確認する |
| M13 | 行が不明な場合の保守的な秘匿を解除しても成功した | 合成の秘密情報を含む入力に対し、検出器が行0を返す場合を確認する。秘密のない入力は保持する対照も用意する |
| M14 | 列が不明な場合の保守的な秘匿を解除しても成功した | 認証情報のある行で検出器が列0を返す場合を確認する。短い断片だけでは秘密の構文を再判定できない例を含める |

M13・M14は、位置が不明な場合も保守的に扱う[既存の秘匿契約](../architecture/EVIDENCE-PRIVACY.md)に関する不足です。ただし、変異を入れたときに見逃したという結果であり、現在の製品で秘密情報の流出を実証したものではありません。M03・M04は044で実行が記録されなかった昇格処理とも一致します。

M20は、証明書DERの末尾に余分なデータがあるかを確かめる最初の検査を省く変異です。その後も`certificate_attributes`→`validate_certificate_layout`→`sequence_fields`で同じDER全体を検査し、余分なデータを拒否します。余分なデータがなければ省いた条件は元から偽です。そのため、受理・拒否と返す属性については振る舞いが変わらない等価変異と判断します。処理時間の同一性を主張するものではありません。この1件をテスト不足とは数えません。

今回の成果は、上記の弱点を測定と根拠付きで特定したことです。045の受入条件は評価の完了であり、全ての見逃しの解消や検出率100%ではありません。表のテスト追加は改善案として残し、製品の判断や当初の受入条件は変更していません。

分類処理については、小さなRustのテストを実際にコンパイル・実行し、成功、アサーション失敗、未定義の値によるコンパイルエラー、時間切れの4例が正しく分類されることを確認しました。この4例は計測処理の対照で、製品の20変異には含めません。
