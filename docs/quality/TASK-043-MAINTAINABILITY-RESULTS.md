# TASK-043の保守性改善

今回の対象は、完了したFP4件・FN40件の修正に残った重複管理です。以前の入力・正解・測定・受入は保持し、変更前の作業ツリーとバイナリを別に保存しています。基点HEADは`0a281e90d4e7e0402e2dd5d0aa19a7249c5373bf`、ブランチは`codex/quality-assessment-model`です。HEADだけではなくソースhashで版を特定します。

## 削除・集約したもの

| 調査した問題 | 対応 | 残す知識との区別 |
|---|---|---|
| 6規則のpattern/scope/kindがYAMLとRustで二重管理 | 正本YAMLをビルドへ取り込み、そこから既定規則の照合情報を得る | Rustにはどの解析handlerがどの規則を扱うかという識別だけを残す |
| Nodeの方式名リストとPythonの生成API名リストがYAMLと重複 | 既にロードしたcompiled patternで正規化した呼出しを判定。部分一致ではなく対象全体の一致を要求する | 暗号moduleの識別や鍵・署名オブジェクトの意味は引き続きAPI別に解釈する |
| Pythonの構文回復用patternを別途再定義・再compile | 同じロード済みpatternを使う | 構文エラーでも観測を保持する方針は変えない |
| 共通の証拠抽出がRustの規則IDに分岐 | 呼出し先まで／第1引数まで、の操作を明示的に分離する | 言語側が秘密を含み得る引数を証拠に含めない範囲を選ぶ |
| Rustのcrate名を通常解析と不完全useの正規表現に重複記載 | crate一覧から回復用patternを生成し、一度だけcompileする | 対応する実APIのcrate名・型・鍵pairの意味は保持する |

評価ケースID、検体名、行番号に基づく製品コードの例外は見つかりませんでした。規則IDは解析handlerや所見の識別に必要な参照として残しています。品質メタデータのrule snapshotは過去のレビューと版照合の証拠であり、実行時の判定には使いません。

## 維持する範囲

言語のスコープ、import、分割代入、型、Node/PyCA/RustCryptoのAPI、gemspec/Gradleの文法などは一律に解釈できないため残しています。カスタム規則の変更pattern/scope/kindは従来の汎用matcherへ戻します。規則YAML、ID、分類、公開型・Schema、CLI、新規依存は変更しません。

正本のYAMLはコンパイル時に取り込むため、実行時にリポジトリの内部パスを読みません。空の作業ディレクトリから、コピーした規則と入力だけを指定して動作することも試験します。現行のソース配布・path installと同じく、ビルドにはリポジトリ全体を使います。未確立のcrates.io単独公開を今回の対応範囲へ追加しません。

## 検証方針

新しいテストでは、テスト用YAMLだけに記した仮の方式・生成シンボルについて、別名import、有限loop、構文回復が選択定義に従うことを確認します。修正前はNode/Pythonとも0件で失敗し、修正後に成功しました。これは仮の方式が実在・実装されているという主張ではなく、規則定義をRustへ再転記せず追従できるかを調べる対照です。

固定した5コーパスは、既存runner/evaluator/reporterを使って変更前後を各3回測定します。TP/FP/FN/TNだけでなく、所見・位置・ID・診断・順序の正規化したdigestを照合します。以前から残る旧注釈の数値信号を、保守性変更の退行と混同しません。正解を調整して一致させることはしません。
