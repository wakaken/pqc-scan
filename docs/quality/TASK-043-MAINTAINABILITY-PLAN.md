# TASK-043：規則の重複管理をなくす

ユーザーの追加依頼により、043の検出修正に残った不要な個別対応と重複定義を整理する。完了済みの44件の修正記録・正解・測定は保持する。

## 調査と設計

- 評価ケースID、検体名、行番号による製品コードの例外は見つからない。
- 既定6規則のpattern/scope/kindがYAMLと`source_facts.rs`で二重管理されている。
- Nodeの方式名リストとPythonの生成API名リストも、規則patternの部分的な再定義になっている。
- `Facts::call`がRustの規則IDを見て証拠範囲を変える処理は、共通機能へ規則固有の知識を持ち込んでいる。
- スコープの言語差、Node/PyCA/RustCryptoのimport・戻り値の意味、gemspec/Gradleの文法、既知package識別は必要な知識として残す。

選択肢は、(1)現行YAMLをコンパイル時に取り込み既定規則との照合・方式判定に再利用、(2)YAMLに新しい解析DSLを追加、(3)一般的な多言語の意味解析器へ置換、の三つ。主担当は(1)を採用する。(2)は設定互換性と検証面を増やし、(3)は今回の範囲を超える。ユーザーが承認した「不要な個別対応・二重管理の解消」の範囲で実施し、検出範囲・分類・公開形式は変えない。

`source_facts`内に小さな既定規則カタログを置き、現行YAMLを`include_str!`で参照する。起動後に一度だけ既存serde_yamlで読み、外部ファイルI/Oや新規依存は増やさない。pattern/scope/kindはYAMLから得る。Rustには対応する意味解析handlerの識別だけを残す。カスタム規則の変更pattern/scope/kindは従来どおり汎用matcherへ戻す。Nodeの固定引数とPythonの正規化した呼出しは、ロード済みcompiled patternへ完全一致させて判定する。未知の値を推測せず、文字列の一部一致で別の式を陽性にしない。

ビルドは現在サポートするリポジトリ全体からのworkspace/path installが前提。crates.io公開は既存の配布方針でも未確立で、今回追加しない。規則YAMLの変更はCargoのinclude依存として再ビルドに反映する。

## 手順と受入条件

1. 開始HEAD/dirty差分、ソース・規則・コーパス・旧バイナリを新しいtargetディレクトリへ保存する。
2. 既定規則とカスタム規則の分岐、変更した方式定義への追従、引用符を含む不明値の否定をテストする。実装前の失敗を確認する。
3. 重複pattern/scope/kindとNode/Pythonの再列挙を削除する。証拠範囲の選択は明示した共通操作へ分離する。必要な言語/APIの解釈は維持する。
4. 既存28検出試験・CLI出力試験と、固定043-v2・042-v2・旧57単位の変更前後を同じ評価器・正解で比較する。成績だけでなく、正規化した所見・位置・ID・診断・順序の意味が同じことを確認する。コーパスを再調整しない。
5. fmt/workspace tests/Clippy/release build/Python/Nodeを実行する。自己スキャンの有限なsource hashは必要なものだけ更新し、許可所見を増やさない。
6. 実装後に実装レビュー1名、主担当の必要試験後に試験妥当性レビュー1名を使う。各段階の担当は修正後も再利用する。未解消の必須事項があればdoneにしない。
7. 新しい測定・レビュー・受入を追加し、過去の043の証拠を上書きせず、最終ソースと結び付ける。

完了は保守性改善と既存挙動維持に限定する。一般的な型推論・外部module解決・全API対応・新しい精度保証の完成とはしない。数値ゲートとRisk/Severity/Confidenceは維持する。
