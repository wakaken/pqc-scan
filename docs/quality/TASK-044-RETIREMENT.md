# TASK-044 計測基盤の整理

044では、重要な処理のうちテストが届いていない箇所と、追加の検証手法を使える範囲を調べました。その後、ユーザーの指示に従って計測基盤を整理し、coverage（テスト到達率）の計測と共通の隔離基盤を残して、Miri専用の実装を通常のテスト領域から取り除きました。

Miriは常設の検証基盤として保守せず、製品全体のMiri合格も目標にしません。今後使う場合は、調べたいリスクや疑わしい不具合を先に決め、元のcrateにあるテストから対象を絞って判断します。過去の実行結果と再現に必要なコードは、調査資料として保存しています。

整理を始めた時点のHEADは`f8aff1888525f0f3e350a734166c12c6de3e71ed`、作業ブランチは`codex/quality-assessment-model`です。041〜043などの既存変更と、044の未コミットの成果を引き継ぎました。Miri専用実装の整理では、製品のRustコード、Cargo設定、検出ルール、公開スキーマ、CIのprotocols停止条件を変更していません。後述するdevelop統合時の修正とは区別します。

## 残したものと取り除いたもの

- `tests/quality/task044/coverage.py`と集計テストを残しました。分岐が未測定の状態と到達率0%を区別し、計算の分母がない箇所や対象外のファイルも分けて扱います。
- `entry.py`のLLVMによる計測を残しました。設定ごとにプロファイルを分け、計測したバイナリとソースを識別し、生のプロファイルデータの容量を管理します。
- 共通コンテナーの隔離条件を維持しました。root以外のユーザーで実行し、ソースとルートファイルシステムは読み取り専用にします。外部通信を禁止し、環境変数を引き継がず、使用資源と持ち出せるデータ量に上限を設け、終了後にコンテナーを削除します。
- Miri専用の`miri_followup.py`、`miri_range.py`、`miri_support.py`、`miri_os_selection.json`、`test_miri044.py`を通常のテスト領域から取り除きました。
- `entry.py`からMiriの試行処理と、ソースの一部を切り出したcrateの生成処理を取り除きました。共通の実行窓口からもMiri専用の4ケースを削除しています。Miriを繰り返し試す仕組みや結果の解析処理は、常設基盤として保守しません。

## 現在の実行経路

通常の`coverage044`はRust 1.93.1を使い、workspaceの通常設定と全機能を有効にした設定で、行・領域の到達率を計測します。Miriの読み込みや実行、nightlyの呼び出しはありません。初期調査で使った、nightlyの識別情報を確かめる小規模な試行も通常の実行経路から外しました。

分岐の到達率を測るときは、`coverage044-branch`を明示的に指定します。固定したnightly 2026-02-12で、通常設定と全機能を有効にした設定を計測します。nightlyの指定はcoverage側で管理し、Miri用モジュールには依存しません。

対象環境は従来どおりLinux arm64です。通常の計測にはRust 1.93.1と対応するLLVMツール、分岐の計測には固定したnightlyと対応するLLVMツールが必要です。汎用のprotocolイメージに、これらが揃っているわけではありません。ツールの準備と計測対象の実行は分けています。

次の例では、既存の固定イメージと依存関係を固定したキャッシュを使い、共通コンテナーの隔離条件の下で実行します。分岐を測る場合は、`case`を`coverage044-branch`に変えます。Miriのsysrootは不要です。

```python
import sys
sys.path.insert(0, 'tests/protocol')
from container_runner import execute
execute(immutable_image_id, new_output_directory, case='coverage044', timeout=1800)
```

この例には、ツールを含むイメージの取得や導入の処理は含まれません。再実行するときは、ツールの版とソースが過去の測定時と同じか確認し、結果を新しいディレクトリに保存します。

## GitHubのCIで見つかったRSSテストの修正

統合後のHEAD `b1b1488`を対象とする[初回CI](https://github.com/wakaken/pqc-scan/actions/runs/43382596747)では、Rust、fmt、clippy、Nodeのチェックは成功しましたが、PythonのRSS比較テスト1件が失敗しました。

このテストは、メモリを多く使う子プロセスと少なく使う子プロセスの最大RSSを比べるものです。大きい方の子プロセスに固定で32MiBを割り当てていましたが、親プロセス由来のRSSがそれを上回ると、Linuxでは両者の最大RSSが同じになることを再現しました。計測処理や過去のRSS値は変えず、大きい方の子プロセスが親自身の最大RSSを超える量のメモリを確保し、実際にアクセスするようにテストを修正しました。

親のRSSが大きいLinux環境で、修正前の失敗と修正後の成功を確認しました。また、累積値を返す誤った実装ではテストが失敗することも確かめています。Linuxの計測テスト6件とmacOSの品質テスト59件が成功し、既存二者のレビューも受け入れられました。[修正の検証記録](task044-ci-fix-20261113/VALIDATION.json)と[レビュー](task044-ci-fix-20261113/REVIEWS.md)を参照してください。対象ソース、実行ログ、正確な再現手順を保存しています。修正後は044を`done`に戻し、最終HEADのCIを確認してからマージする手順としていました。
