# Oracle provenance and limitations

The historical 042 truth and 93/5/25 labels remain unchanged. The new 83 text
pairs are hand-authored explicit syntax/declaration observations; expected
counts were fixed before execution, rather than generated by running a rule
against its own pattern. Inputs reference public names and synthetic version/
credential labels. No specimen executes code or connects to a network.
Existing rule purpose/method limits in RULE-QUALITY-METADATA.json and reviewed
042/043 source contracts are reused; these are implementation-exposed controls,
not blind independent holdout or a per-language completeness certification.

The Java constructor's first argument denotes modulus bits in the
[Oracle Java SE 25 API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/security/spec/RSAKeyGenParameterSpec.html).
This independently supports the declared reference fact; neither a constructor
nor its detection proves that a deployed key was created or used.

Certificate controls reuse the unchanged fixed assessment clock, public fixtures,
parsed-attribute truth cases and exact-rule assertions from certificate_policy.rs.
The two added SLH-DSA containers use OID 2.16.840.1.101.3.4.3.20, assigned to
SLH-DSA-SHA2-128s by [RFC 9909 section 3](https://www.rfc-editor.org/rfc/rfc9909.html#section-3).
They deliberately retain the RSA fixture's other public bytes: they are synthetic
OID observations with Partial attribute status, not valid SLH keys or signatures.
The size/mode requirements and signature/trust verification are not inferred from
an observed OID. Original time, malformed-container and conventional-key facts
are reused without changing their truth or signatures.

  the existing rule explicitly names them. New references are additive; no YAML

All public-primary-source lookups above were checked on 2026-11-17. They provide
input facts, not claims of RFC/FIPS certification or comprehensive implementation
conformance. The new study is evaluated by the existing two review identities.

## ASN.1 parameter-type correction

The new non-OID control failed with parameters_kind=oid. The pinned
asn1-rs 0.7.1 Oid::try_from(&Any) constructs Oid from content without checking
its tag. Null/Sequence conversions also cannot substitute for full class/shape
checks. The public attribute extractor now checks universal class, exact tag
and constructed/primitive shape before reporting OID/NULL/SEQUENCE/INTEGER facts.
This follows the already declared DER/algorithm-parameter types in
[RFC 3279](https://www.rfc-editor.org/rfc/rfc3279.html) and
[RFC 4055](https://www.rfc-editor.org/rfc/rfc4055.html). No new cryptographic risk
policy or public storage schema is introduced. Invalid lookalikes can lose false
OID/curve/key-size facts and retain incomplete status; sequence parameters can
change from incorrect oid to other (native unknown). That compatibility effect
is explicit, not filtered from comparison. Wrongly tagged parameter values do
not become valid keys, algorithms or signatures merely because their bytes
resemble a known OID.
